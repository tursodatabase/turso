# PRAGMA Statements

PRAGMA statements are special commands used to query or modify database configuration, retrieve metadata, and control database behavior. Unlike standard SQL, PRAGMAs are specific to SQLite and Turso.

## Syntax

```sql
PRAGMA pragma-name;
PRAGMA pragma-name = value;
PRAGMA pragma-name(value);
```

## Database Metadata

### database_list

Returns one row for each attached database.

```sql
PRAGMA database_list;
-- seq | name | file
-- 0   | main | /path/to/database.db
```

### page_count

Returns the total number of pages in the database file.

```sql
PRAGMA page_count;
-- 42
```

### page_size

Returns or sets the page size of the database. The page size can only be set before any tables are created. On an existing database, the new size is not applied to it, but later [`VACUUM INTO`](/docs/sql-reference/statements/vacuum#vacuum-into) statements on the same connection use it for the destination.

```sql
PRAGMA page_size;
-- 4096

PRAGMA page_size = 8192;
```

### max_page_count

Returns or sets the maximum number of pages allowed in the database file.

```sql
PRAGMA max_page_count;
PRAGMA max_page_count = 1000000;
```

### freelist_count

Returns the number of unused pages in the database file.

```sql
PRAGMA freelist_count;
```

### encoding

Returns the text encoding used by the database.

```sql
PRAGMA encoding;
-- UTF-8
```

### schema_version

Returns the schema version number. This value is incremented each time the schema changes.

```sql
PRAGMA schema_version;
-- 5
```

### application_id

Returns or sets the application ID stored in the database header. Applications can use this 32-bit integer to identify the database file format.

```sql
PRAGMA application_id;
PRAGMA application_id = 12345;
```

### user_version

Returns or sets the user version number. This is a 32-bit integer available for application use.

```sql
PRAGMA user_version;
PRAGMA user_version = 3;
```

## Schema Introspection

### table_info

Returns one row for each column in the named table.

```sql
PRAGMA table_info(table-name);
```

| Column | Type | Description |
|--------|------|-------------|
| cid | INTEGER | Column index (0-based) |
| name | TEXT | Column name |
| type | TEXT | Declared type name |
| notnull | INTEGER | 1 if NOT NULL constraint exists |
| dflt_value | TEXT | Default value expression, or NULL |
| pk | INTEGER | 1 if column is part of the PRIMARY KEY |

```sql
CREATE TABLE users (id INTEGER PRIMARY KEY, name TEXT NOT NULL, email TEXT);
PRAGMA table_info(users);
-- cid | name  | type    | notnull | dflt_value | pk
-- 0   | id    | INTEGER | 0       |            | 1
-- 1   | name  | TEXT    | 1       |            | 0
-- 2   | email | TEXT    | 0       |            | 0
```

### table_xinfo

Similar to `table_info` but also includes hidden columns and additional metadata.

```sql
PRAGMA table_xinfo(table-name);
```

Returns the same columns as `table_info` plus a `hidden` column (0 for normal columns, non-zero for hidden columns in virtual tables).

### table_list

Returns one row for each table and view in the database.

```sql
PRAGMA table_list;
-- schema | name    | type  | ncol | wr | strict
-- main   | users   | table | 3    | 0  | 0
-- main   | orders  | table | 4    | 0  | 0
```

### index_list

Returns one row for each index on the named table.

```sql
PRAGMA index_list(table-name);
-- seq | name           | unique | origin | partial
-- 0   | idx_email      | 1      | c      | 0
```

| Column | Type | Description |
|--------|------|-------------|
| seq | INTEGER | Index sequence number |
| name | TEXT | Index name |
| unique | INTEGER | 1 if the index is UNIQUE |
| origin | TEXT | `c` for CREATE INDEX, `u` for UNIQUE constraint, `pk` for PRIMARY KEY |
| partial | INTEGER | 1 if the index is a partial index |

### index_info

Returns one row for each column in the named index.

```sql
PRAGMA index_info(index-name);
-- seqno | cid | name
-- 0     | 2   | email
```

An expression column (for example `CREATE INDEX i ON t(lower(name))`) has `cid` -2 and a NULL `name`.

The PRIMARY KEY of a `WITHOUT ROWID` table is reported as an index named `sqlite_autoindex_<table>_1`. Passing the table's name to `index_info` or `index_xinfo` also describes that index.

### index_xinfo

Similar to `index_info` but includes additional columns.

```sql
PRAGMA index_xinfo(index-name);
```

### foreign_key_list

Returns one row per parent key column of each foreign key constraint on a table. `id`
numbers the constraints, `seq` is the position of the column within that constraint, and
`from` and `to` are the child and parent columns. `on_update` and `on_delete` are
`NO ACTION` unless the constraint declares an action, and `match` is always `NONE`.
Constraints are reported newest declaration first, so a table-level `FOREIGN KEY` clause
written last has `id` 0.

```sql
PRAGMA foreign_key_list(child);
-- id | seq | table  | from     | to   | on_update | on_delete | match
```

An optional schema qualifier selects the database, and the same rows are available as the
`pragma_foreign_key_list()` table-valued function. A name that is not a table with
foreign keys, and a missing table argument, return no rows rather than an error.

```sql
PRAGMA main.foreign_key_list(child);
SELECT * FROM pragma_foreign_key_list('child');
```

### function_list

Returns one row for each SQL function available.

```sql
PRAGMA function_list;
-- name | builtin | type | enc | narg | flags
```

### module_list

Returns one row for each virtual table module registered on the connection, in arbitrary
order.

```sql
PRAGMA module_list;
-- completion
-- generate_series
```

A freshly opened database reports the built-in `generate_series` module, which is
compiled in through the default `series` feature. The `tursodb` shell also registers a
`completion` module for tab completion, so it shows up when you run the pragma there.
Virtual table modules registered by loaded extensions show up here as well. The pragma takes no arguments: a write form such as
`PRAGMA module_list = 1;` is accepted and does nothing.

### pragma_list

Returns the list of all supported PRAGMA commands.

```sql
PRAGMA pragma_list;
```

## Database Configuration

### journal_mode

Returns or sets the journal mode.

```sql
PRAGMA journal_mode;
-- wal

PRAGMA journal_mode = wal;
```

Turso supports WAL (Write-Ahead Logging) mode. Rollback journal modes (DELETE, TRUNCATE, PERSIST, MEMORY) are not supported.

<Info>
**Turso Extension**: Turso supports an experimental MVCC journal mode for concurrent writes:

```sql
PRAGMA journal_mode = mvcc;
```

When MVCC mode is active, you can use `BEGIN CONCURRENT` for optimistic concurrent write transactions. See [Transactions](/docs/sql-reference/statements/transactions#begin-concurrent) for details.
</Info>

### auto_vacuum

Returns or sets the auto-vacuum mode. The bare form returns the current mode as an integer.

```sql
PRAGMA auto_vacuum;              -- 0 (none), 1 (full), or 2 (incremental)
PRAGMA auto_vacuum = none;       -- same as = 0
PRAGMA auto_vacuum = full;       -- same as = 1
PRAGMA auto_vacuum = incremental; -- same as = 2
```

Auto-vacuum is experimental: setting a mode other than `none` fails with
`Autovacuum is not enabled. Use --experimental-autovacuum flag to enable it.`
unless the database was opened with the `--experimental-autovacuum` flag. Writing
`none` is always allowed, and unrecognized names or numbers are treated as `none`.
The `incremental` mode can be set but is not supported yet: the next write fails with
`Incremental auto-vacuum is not supported`.

Like SQLite, the mode is fixed once page 1 of the database file exists: setting the
pragma after the database has been initialized is silently ignored. Opening a database
that already has auto-vacuum enabled without the flag logs a warning and opens the
connection read-only.

### cache_size

Returns or sets the suggested maximum number of database pages held in memory.

```sql
PRAGMA cache_size;
PRAGMA cache_size = 2000;          -- positive: number of pages
PRAGMA cache_size = -2000;         -- negative: kilobytes of memory
```

### cache_spill

Enables or disables cache spilling (writing dirty pages to the WAL before the cache is full).

```sql
PRAGMA cache_spill;
PRAGMA cache_spill = 0;    -- disable
PRAGMA cache_spill = 1;    -- enable
```

### synchronous

Controls the fsync behavior for durability guarantees.

```sql
PRAGMA synchronous;
PRAGMA synchronous = OFF;    -- no fsync (fastest, risk of corruption on crash)
PRAGMA synchronous = NORMAL; -- no fsync on commit, fsync at checkpoint
PRAGMA synchronous = FULL;   -- fsync after every transaction (safest)
```

Turso accepts `OFF`, `NORMAL`, and `FULL`, by name or by number (`0`, `1`, `2`).
Anything else becomes `FULL`. `PRAGMA synchronous;` returns the number of the mode
you set.

With `NORMAL`, a commit does not fsync the WAL. The fsyncs happen at checkpoint
time instead.

SQLite has a fourth level, `EXTRA`. Turso does not have it, and sets `FULL` for any
value it does not know, `EXTRA` included.

### temp_store

Controls where temporary tables and indexes are stored.

```sql
PRAGMA temp_store;
PRAGMA temp_store = 0;    -- DEFAULT
PRAGMA temp_store = 1;    -- FILE
PRAGMA temp_store = 2;    -- MEMORY
```

### busy_timeout

Sets the busy timeout in milliseconds. When a table is locked, Turso waits up to this many milliseconds before returning SQLITE_BUSY.

```sql
PRAGMA busy_timeout;
PRAGMA busy_timeout = 5000;   -- 5 seconds
```

### query_only

When enabled, prevents any changes to the database.

```sql
PRAGMA query_only = 1;    -- enable read-only mode
PRAGMA query_only = 0;    -- disable read-only mode
```

### full_column_names / short_column_names

Legacy SQLite naming pragmas, kept for compatibility. Each is a per-connection boolean.
As in SQLite, `full_column_names` is off by default and `short_column_names` is on by
default. The read form returns `0` or `1`. A write enables the flag for `ON`, `TRUE`,
`YES` (case-insensitively) or any positive number, and disables it for anything else.

```sql
PRAGMA full_column_names;      -- 0
PRAGMA short_column_names;     -- 1
PRAGMA full_column_names = 1;
PRAGMA short_column_names = 0;
```

They only affect the names reported for result columns, never the data:

- With `full_column_names` on, a column reference is named `TABLE.COLUMN` instead of the
  default expression-text name. `SELECT *` expands to those prefixed names only when
  `short_column_names` is also off.
- With `short_column_names` on (and `full_column_names` off), a column reference is
  named with just its column name.
- An explicit `AS` alias always wins over both.

SQLite deprecated both pragmas; prefer naming output columns with `AS` aliases in the
query.

### foreign_keys

Enables or disables foreign key constraint enforcement.

```sql
PRAGMA foreign_keys;
PRAGMA foreign_keys = ON;
PRAGMA foreign_keys = OFF;
```

Foreign key enforcement is off by default for SQLite compatibility.
Changing this setting is a no-op while a transaction or savepoint is open.

### legacy_file_format

Accepted and ignored. SQLite dropped the legacy file format and made this PRAGMA a
no-op, and Turso matches it: the query returns no rows, and a value assigned to it has
no effect.

```sql
PRAGMA legacy_file_format;      -- no rows
PRAGMA legacy_file_format = 1;  -- accepted, no effect
```

### empty_result_callbacks

Accepted for compatibility, but has no effect. SQLite deprecated this pragma long ago
(it controlled whether callbacks still fired when a query returned no rows, which only
matters to the C API callback loop). In Turso both forms are no-ops: the read form
returns no rows, and the write form accepts any value without changing behavior.

```sql
PRAGMA empty_result_callbacks;        -- returns no rows
PRAGMA empty_result_callbacks = ON;   -- accepted, does nothing
```

### ignore_check_constraints

When enabled, CHECK constraints are not enforced.

```sql
PRAGMA ignore_check_constraints = 1;   -- disable CHECK constraints
PRAGMA ignore_check_constraints = 0;   -- enable CHECK constraints
```

### data_sync_retry

Controls whether Turso retries a disk sync (fsync) after a failure instead of treating it as fatal.

```sql
PRAGMA data_sync_retry = 1;   -- retry on sync failure
PRAGMA data_sync_retry = 0;   -- do not retry (default)
```

### fullfsync

<Warning>
**Apple platforms only.** `F_FULLFSYNC` is a macOS and iOS system call. On other platforms
Turso does not know the pragma name and ignores the statement, like any other unknown
pragma, so it silently does nothing there.
</Warning>

On Apple platforms, enabling this makes Turso use `F_FULLFSYNC` instead of `fsync` when it
syncs the database file, which also asks the storage device to flush its own cache to
media. Off by default. It changes which sync call is used, not when the sync happens:
`synchronous` still decides that.

```sql
PRAGMA fullfsync;        -- 0
PRAGMA fullfsync = 1;    -- use F_FULLFSYNC
PRAGMA fullfsync = off;  -- use fsync again
```

### require_where

<Info>
**Turso Extension**: a safety pragma with no SQLite equivalent.
</Info>

When enabled, Turso rejects any `UPDATE` or `DELETE` that does not include a `WHERE` clause, guarding against accidental full-table modifications. `i_am_a_dummy` is an alias that enables the same behavior.

```sql
PRAGMA require_where = 1;
DELETE FROM users;            -- rejected: no WHERE clause
DELETE FROM users WHERE id = 1;  -- allowed

PRAGMA i_am_a_dummy = 1;      -- equivalent to require_where = 1
```

### count_changes

Off by default. When enabled, each top-level `INSERT`, `UPDATE` and `DELETE` returns one
row with the number of rows it changed, in a column named `rows inserted`, `rows updated`
or `rows deleted`. Trigger bodies, foreign key actions and other nested statements never
emit count rows, and a statement with a `RETURNING` clause does not either, since it
already returns rows.

```sql
PRAGMA count_changes;          -- count_changes: 0 (default)
PRAGMA count_changes = 1;
INSERT INTO t VALUES (1), (2); -- rows inserted: 2
UPDATE t SET x = x + 1;        -- rows updated: 2
DELETE FROM t WHERE x = 1;     -- rows deleted: 1
PRAGMA count_changes = off;    -- statements return no rows again
```

### locking_mode

Returns the database locking mode, which is always reported as `exclusive`.

```sql
PRAGMA locking_mode;
-- exclusive

PRAGMA locking_mode = exclusive;
```

<Warning>
Turso only accepts the value `EXCLUSIVE`, in any letter case and with or without quotes.
SQLite's default value `NORMAL` is rejected:

```sql
PRAGMA locking_mode = normal;
-- Parse error: locking_mode must be EXCLUSIVE
```

Writing the pragma does not change how Turso locks the database file. It only checks the
value and then reports `exclusive`, the same as the read form. So a portable script that
sets `locking_mode` back to `NORMAL` when it finishes will fail here even though it works
on SQLite. This matches the `Partial` entry for `PRAGMA locking_mode` in `COMPAT.md`.
</Warning>

### fts_merge_threshold

<Info>
**Turso Extension**: write-path merging for the `fts` index method has no SQLite equivalent.
</Info>

Controls how many visible segments a `fts` index may accumulate before Turso merges them
as part of the write path. After each statement that flushes the index, Turso compares the
visible segment count against the threshold and merges the excess. The default is 32.
Setting it to `0` disables write-path merging. The value applies to the current connection;
new connections start from the default again.

```sql
PRAGMA fts_merge_threshold;        -- 32
PRAGMA fts_merge_threshold = 8;    -- merge once the index has more than 8 visible segments
PRAGMA fts_merge_threshold = 0;    -- disable write-path merging
PRAGMA fts_merge_threshold = -1;   -- error: must be 0 (disabled) or a positive integer
```

## Integrity Checks

### integrity_check

Performs a thorough integrity check of the entire database.

```sql
PRAGMA integrity_check;
-- ok

PRAGMA integrity_check(N);    -- check only the first N errors
```

Returns `ok` if no problems are found, otherwise returns one row per error.

For custom index methods, this checks the structure of their backing B-trees.
It does not compare their custom records with table rows as it does for ordinary indexes.

### quick_check

Performs a faster but less thorough integrity check than `integrity_check`.

```sql
PRAGMA quick_check;
```

## Debugging

### vdbe_trace

Turns tracing of the bytecode program on for this connection. Off by default. A program
stepped while it is on writes to standard error: one line for each register the previous
opcode changed, written as `R[i] = value`, then the opcode that is about to run, printed the
way `EXPLAIN` prints it. The listing of a program starts with a `VDBE Trace:` line. A
register that holds an aggregate state or a record prints as `<aggregate>` or `<record>`
instead of a value.

```sql
PRAGMA vdbe_trace = 1;    -- trace programs on this connection
PRAGMA vdbe_trace = off;  -- stop tracing
```

Reading the pragma does nothing: `PRAGMA vdbe_trace;` returns no rows and does not report
the current setting.

## WAL Operations

### wal_checkpoint

Forces a WAL checkpoint.

```sql
PRAGMA wal_checkpoint;
```

A checkpoint writes pages from the WAL file back to the database file.

Inside a transaction, the checkpoint fails with `database table is locked` once the transaction has read or written the database. Right after `BEGIN`, before any read, it runs normally.

### wal_autocheckpoint

Returns or sets how many pages the WAL can hold before a commit on this connection runs a checkpoint. The default is 1000 pages. Zero or a negative value turns automatic checkpoints off.

```sql
PRAGMA wal_autocheckpoint;
PRAGMA wal_autocheckpoint = 1000;
PRAGMA wal_autocheckpoint = 0;    -- turn automatic checkpoints off
```

The setting applies only to the connection that sets it. Closing the last connection to the database still checkpoints the WAL. In MVCC mode the setting has no effect; use `mvcc_checkpoint_threshold` instead.

## MVCC Tuning

<Info>
**Turso Extension**: these pragmas apply only when MVCC mode is enabled (`PRAGMA journal_mode = mvcc`).
</Info>

### mvcc_checkpoint_threshold

Sets the amount of committed work that accumulates before Turso triggers an MVCC checkpoint.

```sql
PRAGMA mvcc_checkpoint_threshold = 1000;
```

### mvcc_gc_threshold

Sets the threshold that controls how aggressively Turso garbage-collects obsolete MVCC row versions.

```sql
PRAGMA mvcc_gc_threshold = 1000;
```

### mvcc_group_commit

Lets concurrent MVCC commits batch their logical-log writes so one of them appends
every waiting transaction's record and the whole batch shares a single fsync.
Off by default.
Exclusive transactions started with `BEGIN IMMEDIATE` or `BEGIN EXCLUSIVE` commit
on the solo path and do not join the queue. The setting applies to every
connection on the store.

```sql
PRAGMA mvcc_group_commit = on;
```

## Change Data Capture

<Info>
**Turso Extension**: Change Data Capture (CDC) is a Turso-specific feature that tracks all data changes for replication, auditing, and reactive applications.
</Info>

### capture_data_changes_conn

Enables CDC for the current connection. Changes are captured to a designated table.

```sql
PRAGMA capture_data_changes_conn('mode');
PRAGMA capture_data_changes_conn('mode,table_name');
```

The legacy name `unstable_capture_data_changes_conn` is still accepted for backwards compatibility.

| Parameter | Description |
|-----------|-------------|
| mode | Capture mode: `off`, `id`, `before`, `after`, `full` |
| table_name | Custom table name for storing changes (default: `turso_cdc`) |

#### Capture Modes

| Mode | Description |
|------|-------------|
| `off` | Disable CDC for this connection |
| `id` | Capture only the primary key/rowid of changed rows |
| `before` | Capture row state before changes (for updates/deletes) |
| `after` | Capture row state after changes (for inserts/updates) |
| `full` | Capture both before and after states, plus update details |

#### CDC Table Structure

The CDC table contains the following columns:

| Column | Type | Description |
|--------|------|-------------|
| change_id | INTEGER | Auto-incrementing unique identifier |
| change_time | INTEGER | Unix epoch timestamp |
| change_type | INTEGER | 1 (INSERT), 0 (UPDATE), -1 (DELETE) |
| table_name | TEXT | Name of the changed table |
| id | varies | Primary key/rowid of the changed row |
| before | BLOB | Row data before the change (modes: before, full) |
| after | BLOB | Row data after the change (modes: after, full) |
| updates | BLOB | Updated column details (mode: full) |

#### CDC Examples

```sql
-- Enable full CDC
PRAGMA capture_data_changes_conn('full');

-- Make changes
CREATE TABLE users (id INTEGER PRIMARY KEY, name TEXT);
INSERT INTO users VALUES (1, 'Alice');
UPDATE users SET name = 'Alicia' WHERE id = 1;
DELETE FROM users WHERE id = 1;

-- Query the changes
SELECT change_type, table_name, id FROM turso_cdc;
-- 1  | users | 1    (INSERT)
-- 0  | users | 1    (UPDATE)
-- -1 | users | 1    (DELETE)

-- Use a custom table name
PRAGMA capture_data_changes_conn('full,audit_log');

-- Disable CDC
PRAGMA capture_data_changes_conn('off');
```

CDC respects transaction boundaries. Changes are only recorded when a transaction commits. If a transaction rolls back, no CDC entries are created.

## Encryption

<Info>
**Turso Extension**: At-rest encryption is a Turso-specific feature. This feature is experimental and must be [enabled before use](/docs/sql-reference/experimental-features).
</Info>

### cipher

Sets the encryption cipher for the database.

```sql
PRAGMA cipher = 'aegis256';
```

Supported ciphers:

| Cipher | Key Size | Description |
|--------|----------|-------------|
| `aes128gcm` | 16 bytes | AES-128 in Galois/Counter Mode |
| `aes256gcm` | 32 bytes | AES-256 in Galois/Counter Mode |
| `aegis128l` | 16 bytes | AEGIS-128L |
| `aegis256` | 32 bytes | AEGIS-256 (recommended) |
| `aegis128x2` | 16 bytes | AEGIS-128 with 2x parallelization |
| `aegis128x4` | 16 bytes | AEGIS-128 with 4x parallelization |
| `aegis256x2` | 32 bytes | AEGIS-256 with 2x parallelization |
| `aegis256x4` | 32 bytes | AEGIS-256 with 4x parallelization |

### hexkey

Sets the encryption key as a hexadecimal string.

```sql
PRAGMA hexkey = '2d7a30108d3eb3e45c90a732041fe54778bdcf707c76749fab7da335d1b39c1d';
```

#### Encryption Example

```sql
-- Set cipher and key before creating tables
PRAGMA cipher = 'aegis256';
PRAGMA hexkey = '2d7a30108d3eb3e45c90a732041fe54778bdcf707c76749fab7da335d1b39c1d';

CREATE TABLE secrets (id INTEGER PRIMARY KEY, data TEXT);
INSERT INTO secrets VALUES (1, 'sensitive data');
```

Alternatively, specify encryption parameters in the database URI:

```
file:database.db?cipher=aegis256&hexkey=2d7a30...
```

To open an existing encrypted database, the cipher and key must be provided as URI parameters.
