# SQLite Compatibility

The authoritative compatibility reference is maintained at [`COMPAT.md`](https://github.com/tursodatabase/turso/blob/main/COMPAT.md) in the repository root. It tracks the support status for every SQL statement, expression, function, PRAGMA, C API function, VDBE opcode, and extension.

Refer to that document for the current state of compatibility. It is updated alongside code changes to stay accurate.

## Turso-Specific Extensions

These features extend Turso beyond SQLite compatibility:

| Feature | Description |
|---------|-------------|
| [CREATE TYPE](/docs/sql-reference/statements/create-type) | User-defined types for STRICT tables |
| [CREATE MATERIALIZED VIEW](/docs/sql-reference/statements/create-materialized-view) | Live materialized views with incremental maintenance |
| [BEGIN CONCURRENT](/docs/sql-reference/statements/transactions#begin-concurrent) | Optimistic concurrent write transactions (MVCC) |
| [Vector functions](/docs/sql-reference/functions/vector) | Vector storage, distance calculations, similarity search |
| [Full-text search](/docs/sql-reference/functions/fts) | Tantivy-powered FTS with BM25 scoring |
| [CDC](/docs/sql-reference/pragmas#change-data-capture) | Change Data Capture via PRAGMA |
| [Encryption](/docs/sql-reference/pragmas#encryption) | At-rest database encryption |
| [Custom index methods](/docs/sql-reference/statements/create-index#using-method) | CREATE INDEX ... USING for FTS and custom access methods |
| [NULL ordering in indexes](/docs/sql-reference/statements/create-index#nulls-first-last) | NULLS FIRST/LAST in CREATE INDEX and in table PRIMARY KEY and UNIQUE constraints. A schema using it cannot be opened by stock SQLite |
| stddev() | Standard deviation aggregate function |
| [DEFAULT in VALUES](/docs/sql-reference/statements/insert#default-keyword-in-values) | SQL-standard DEFAULT keyword in INSERT VALUES lists |

## PostgreSQL schema metadata

The PostgreSQL frontend exposes the default `standard public schema` comment in
`pg_catalog.pg_description`. This lets `pg_dump` preserve the default comment on
`public` without emitting an empty `COMMENT ON SCHEMA` statement. User-defined
comments are not persisted.

The public schema reports `pg_database_owner` as its owner, with `CREATE` and
`USAGE` for that role and `USAGE` for `PUBLIC`, matching PostgreSQL's defaults.
The catalogs and role-name lookup expose this built-in role alongside `turso`.
This metadata does not implement role management or permission enforcement.

PostgreSQL schema catalogs preserve mixed-case table and column names, including
declared primary-key, unique, and foreign-key constraint names, in dumps.
Foreign-key definitions quote identifiers and include the parent schema when
the parent table is not visible through the current `search_path`.
Index definitions retain descending keys.

The PostgreSQL frontend executes each `CREATE SCHEMA` or `DROP SCHEMA` statement
as one operation, including its schema elements or cascading drops.
An error or cancellation before commit rolls back the whole operation.
Cancellation after commit does not undo the changes.

## PostgreSQL configuration parameters

`SET`, `SET LOCAL`, `set_config`, `SHOW`, and `current_setting` use the same
built-in parameter validation. `RESET`, `SET ... TO DEFAULT`, and a NULL value
passed to `set_config` restore the parameter's default. `RESET ALL` and
`DISCARD ALL` also reset `application_name`, `search_path`, and custom parameters.
Session changes inside a transaction roll back with the transaction; local
changes last until its end. An implicit-transaction `set_config(..., true)`
returns the validated value without changing the next statement's settings.

`application_name` stores text per connection (default: empty). `search_path`
and dotted custom parameter names retain their existing transaction behavior.
`current_setting(name, true)` returns NULL for unknown parameters.

Other supported parameters describe fixed engine modes. Their effective value
is returned consistently, including after reset:

| Parameter | Effective value | Accepted alternatives |
| --- | --- | --- |
| `DateStyle` | `ISO, MDY` | `ISO`, `MDY`, either order of `ISO, MDY`; case insensitive |
| `IntervalStyle` | `postgres` | Case insensitive |
| `client_encoding` | `UTF8` | `UTF-8`, `UNICODE`; case insensitive |
| `standard_conforming_strings` | `on` | PostgreSQL true spellings |
| `extra_float_digits` | `1` | `2`, `3` (the same shortest-precise output mode) |
| `statement_timeout`, `lock_timeout`, `idle_in_transaction_session_timeout`, `transaction_timeout` | `0` | None; timeouts are disabled |
| `row_security`, `quote_all_identifiers`, `check_function_bodies`, `synchronize_seqscans` | `off` | PostgreSQL false spellings |
| `default_tablespace` | Empty string | None |
| `default_table_access_method` | `heap` | None |
| `xmloption` | `content` | Case insensitive |
| `client_min_messages` | `warning` | Case insensitive |

Unsupported values raise an error. In particular, accepting ISO date output
does not enable other date formats or date input orders; non-ISO date input
remains unsupported. These settings do not add timeout enforcement, row-level
security, function-body validation, synchronized scans, or additional diagnostic
message levels. Previously accepted no-op requests for unsupported modes now
raise an error rather than reporting that those modes took effect.
